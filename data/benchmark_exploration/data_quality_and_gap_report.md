## 2. 是否能构建真实审核问题 benchmark (real_error)？

**结论: 可以。**

审核意见包中的 **comments.jsonl** 包含审核人员对报告具体问题的修改要求，例如:

- "补充注塑机铭牌。注塑机一轮生产多少件产品，生产一轮需要多长时间，良品率多少。不要为了匹配而去匹配"
- "是否每个产品的原辅材料都一致，不一致需分开XX产品需要XX原辅材料"
- "补充配件尺寸，以及原项目产品图片"

这些是**真实的审核问题**，可以作为 benchmark 的 gold label。

**关键优势**:
1. 批注是真实经办人写的，不是模拟生成的
2. body.md 保留了报告原文 + 批注位置标记 [Cxxx]
3. comments.jsonl 提供了批注的完整文本
4. 可以构造"给模型看修改前报告，测试能否发现经办人指出的问题"

**局限性**:
1. 大部分审核意见包对应的是**送审稿**(初审版本)，而非修改后版本
2. 缺少修改后的版本链——无法验证"问题是否被修正"
3. 批注未按问题类型分类(技术核实/合规检查/逻辑验证等)，需要人工标注

## 4. 哪些字段或附件最缺？

| 缺失项 | 影响 | 严重程度 |
|--------|------|---------|
| **修改后版本的报告** | 无法构建 version_diff benchmark | 🔴 高 |
| **批复与原报告的配对关系** | 只有65对已匹配, 大部分批复未与报告关联 | 🔴 高 |
| **行业代码标注** | 审核意见包和clean_pairs中大部分项目未标注行业代码 | 🟡 中 |
| **审核意见的类型标注** | 502条批注未分类(废气/废水/危废/产污系数等) | 🟡 中 |
| **项目统一ID** | 同一项目的不同版本、报告和批复没有统一ID关联 | 🟡 中 |
| **编制单位信息** | 审核意见包中缺少编制单位 | 🟢 低 |
| **审批时间线** | 缺少受理→退改→修改→批复的完整时间线 | 🟡 中 |

## 8. 最终判断

```
B. 当前数据暂时不足以直接构建"完整的" real_error benchmark，
   但足以构建 real_error + cross_check 混合 benchmark。
```

**细化说明**:

- **可以构建 real_error 类型**: 30个审核意见包中的502条批注是真实审核问题
- **但受限于**: 缺少修改后版本报告, 缺少行业代码标注, 缺少批注分类, 缺少统一项目ID
- **需要先做**: 为C2929项目标注行业代码、分类批注类型、筛选高质量题目
- **建议先产出**: 一个 **C2929 real_error benchmark v0.1** (约40-60题), 作为盛之强 benchmark v0.1 的扩展

**不夸大的结论**:
- 有足够的真实错误数据 ✅
- 需要人工标注和筛选才能转化为benchmark ⚠️
- 当前不能直接"一键生成"benchmark ❌
- 但经过2-3轮人工标注+迭代后可以产出高质量benchmark ✅
